Frontend `d610d9e` adopts newer same-account credentials, serializes refresh through Web Locks, and clears old private UI on account switch/logout. It never retries an old account's write as a different account. Late refresh/storage events cannot undo a subsequent login or logout. ## Future billing relaunch

Do not mass-update user/subscription rows to mark everyone paid. Effective access is computed by `bin/access_policy.py` / `db.get_tier`; stored entitlement remains available through `db.subscription_tier` and billing status. New purchases stay paused unless `DUCKY_ACCESS_MODE=tiered` is explicitly configured. Keep the default open until the owner schedules the relaunch.

Relaunch is a coordinated product release, not just an environment toggle: restore and review the public pricing include/navigation, app account billing entry and frontend build policy, then validate the API catalogue, every rail, existing renewals/receipts and Telegram command/deep-link menus. The retained frontend billing view, bilingual plan strings, payment adapters, webhooks, Stars receipt processing and order history are the implementation reference. Compare selectively against the backup branches so subsequent research/auth/source fixes are retained. Keep sponsorship separate from access rights.
