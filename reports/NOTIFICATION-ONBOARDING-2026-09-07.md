# Telegram sign-in, email verification and delivery preferences

Status: core notification UI published as a680afb5 on Pages 40102f36, against backend 9faffcb. Its exact frontend release passed 258 Node tests. Production browser checks read an existing verified account's actual disabled email and unlinked Telegram states; no preferences, profile fields or test sends were changed. Real receiving-account acceptance and the final demo remain pending. The widget-based connection UI later shipped with frontend 797f51f6 / Pages 81dc329f, but its actual production iframe returned "Bot domain invalid". It was cancelled without changing the account, preferences or recipients. The nonce replacement below is undergoing its own release gate.

An explicit Telegram widget, mini-app or web sign-in sends an account without a verified email to email setup, preserving its safe destination. Stored sessions retain their existing deep links. Saving an address and verifying its six-digit code keep the same account. Verification unlocks Continue; optional profile fields and other account settings are collapsed during setup.

The profile page loads the current email/Telegram preferences, saves explicit choices and re-reads the server result before announcing success. Unverified or unavailable channels cannot be newly enabled. Notification preferences are separate from marketing consent. The backend's accepted creator bridge includes the user's selected creator topics. Failed or throttled verification-code sends leave a persistent resend instruction rather than an apparently completed step. A linked but unreachable Telegram channel requires restarting the bot before it can be enabled.

Connection tests run only after an explicit click. The browser generates one Idempotency-Key UUID per logical test and retains it with the same channels after an unconfirmed HTTP submission. A confirmed queue response starts owner-scoped receipt polling. Each channel has its own pending, claimed, retry, accepted, failed, cancelled or unknown state; service acceptance is not represented as actual receipt/read confirmation. An unresolved result allows status refresh rather than another send. Polling stops on completion, after 12 retries, on cleanup or account change. Wrong message IDs, duplicate/missing channels and contradictory completion flags fail closed.

API contract agreed with the backend owner:

- GET/PATCH `/me/notifications`: strict booleans, channel availability and status, private/no-store.
- POST `/me/notifications/test`: `{channels:[...]}` with optional `Idempotency-Key` UUID; first request and replay return 202 `{message_id,status:"queued"}`. Same owner/key/channels reuses the original message for 24 hours. New logical tests retain 60-second and 3/hour limits.
- GET `/me/notifications/deliveries/{message_id}`: owner-only frozen target statuses. `completed` means all targets are terminal, not simply one provider accepting a request.

Validation: full build and 251 Node tests pass. Focused coverage includes email setup and verified continuation, invalid/expired codes, retained safe Reddit/calendar/alert destinations, Telegram widget bootstrap versus stored-session boot, explicit preference saves, no implicit sends, double clicks, lost response idempotency, partial channel acceptance, unknown results, malformed receipts, polling limit and cross-account/view cleanup.

Mobile browser fixtures: Chinese 390px dark and English 320px light completed email entry, six-digit verification, explicit channel selection, partial Telegram acceptance/email retry and final provider acceptance. Same-account continuation is retained, verified email editing and other settings fold away, no document overflow, and the entire receipt/Continue control can scroll above the bottom navigation. These are UI fixtures, not production sends or proof of inbox receipt.

The production review also found that Google/email accounts needed a Telegram connection entry point. The added connection button reuses the [existing redirect-mode Telegram widget](https://core.telegram.org/widgets/login-legacy), preserving the current account and token. Its ten-minute browser intent binds a random state, account ID and token fingerprint; raw tokens are not placed in its URL or duplicated in the intent. A linking return is intercepted before any Telegram login, stripped from the URL before requests, and validated against the restored account. Only then is its signed payload submitted to `/auth/link/telegram`. An existing binding elsewhere is a conflict, not permission to merge accounts. An invalid Telegram signature does not log the existing Ducky account out. Cancelled/failed widgets clear their intent; missing, expired or mismatched intents never fall through into a Telegram sign-in.

The actual widget failure supersedes its earlier automated checks. The default connection control now uses the existing bot nonce path, without loading that widget. Creating a request returns a short-lived bot link and six-character code shown on the webpage. The bot accepts that code and proposes its Telegram identity; the webpage displays the name/handle and still requires an explicit confirmation. A successful response must contain exactly one Telegram identity matching the displayed candidate, followed by a same-account profile read. The current Ducky token and watchlist remain unchanged. The old signed redirect handler remains only for already-in-flight legacy returns.

The shared nonce controller now handles both existing Telegram sign-in and same-account connection. It validates the nonce/TTL, bounds transient retry waits, expires requests and discards responses after cancellation or account/view changes. Linking cancellation revokes only the original account's request; it never sends a cancellation using a new account's credentials. Link creation, bot confirmation and browser confirmation are separate actions. No notification is sent implicitly.

Replacement validation: 289 Node tests passed, including a bot-confirmed proposal requiring browser consent, duplicate clicks, transient polling failures, lost confirmation responses, pending/expired/conflicting requests, malformed links and identities, same-account checks and cancellation. Existing nonce sign-in still hydrates the profile before success and visibly reports failed hydration. These fixtures use a local-only transport and are not receiving-account evidence.
